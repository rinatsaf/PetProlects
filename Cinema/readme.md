# Cinema Management System — семестровой проект

## Кратко
Веб‑система для управления кинотеатром: каталог фильмов, расписание сеансов, выбор мест на схеме зала, онлайн‑покупка и отправка билетов на email, realtime‑отображение занятости мест и персонализированные рекомендации.

## Выбранная архитектура
- Шаблон: **Clean Architecture + CQRS** — слои `Api (Presentation)`, `Application`, `Domain`, `Infrastructure`. Команды/запросы разделены, чтобы избегать побочных эффектов при чтении данных и упростить масштабирование функциональных блоков (билеты, оплаты, уведомления).
- Почему подходит: система содержит много независимых сценариев (каталог, бронирования, платежи, уведомления). Чтения (каталог, расписание) можно кешировать и масштабировать отдельно от модификаций (бронирование, оплата). Clean Architecture оставляет бизнес‑правила в `Domain` (правила занятости мест, статусы заказов), координацию сценариев в `Application` (CQRS‑handler’ы), инфраструктуру (БД, платежи, email, очереди) изолированной и заменяемой.
- Реализация в проектах:
  - `Cinema.Api` — REST + Swagger, JWT auth, SignalR Hub.
  - `Cinema.Application` — CQRS (MediatR), валидация, маппинги DTO, обработчики событий.
  - `Cinema.Domain` — сущности и бизнес‑правила (бронь с TTL, статус билета, ограничения ролей).
  - `Cinema.Infrastructure` — EF Core + PostgreSQL, Redis для hold, Hangfire jobs, MailKit SMTP, внешние API, логирование.

## Фронтенд
- Стек: **HTML/CSS + Vanilla JS + SignalR JS** (SPA‑подход на страницах бронирования). Асинхронные вызовы через `fetch` к API и WebSocket‑канал SignalR для обновления мест без перезагрузки.
- Альтернатива для демонстрации API: готовится автоматизированная Postman‑коллекция с переменными окружения для одного клика запуска всех кейсов (каталог → создание заказа → оплата → webhook → билет).
- Пояснение работы: страница сеанса запрашивает схему зала (`GET /sessions/{id}`), держит соединение с Hub `session-{id}`; события `SeatHeld/SeatReleased/SeatSold` меняют состояние UI. Покупка — асинхронный POST, ответ содержит redirect на платежную страницу.

## Соответствие backend‑требованиям
- .NET: ASP.NET Core 9 (≥6).
- Swagger: Swashbuckle в `Cinema.Api`.
- БД: PostgreSQL, минимум 5 основных сущностей (см. ниже).
- AuthN/Z: JWT Bearer; роли (`Admin`, `Cashier`, `Customer`), claims/permissions для операций (управление репертуаром, отмена заказов). Principal настраивается в middleware; refresh‑токены в Redis.
- Логирование: Serilog в файл + middleware глобального обработчика ошибок и логирования запросов/ответов.
- Фон/инфраструктура: Hangfire для фоновых задач (освобождение просроченных hold, повторная отправка писем), SMTP (MailKit) для email, Redis для hold, SignalR для realtime.
- Внешний API: TMDB (метаданные фильмов) и/или Dadata (валидация адреса/города кинотеатра).
- Безопасность: antiforgery для cookie‑сценариев, JWT с коротким TTL и refresh, входные модели проходят FluentValidation; HTML‑вывод через безопасные шаблоны, CSP и HttpOnly/SameSite cookies; проверка владения ресурсом (Broken Access Control), двухэтапная проверка статуса заказа перед оплатой, CSRF‑защита для форм, rate limiting на аутентификацию и webhook.

## Модель данных (ядро)
- `User` — роли, refresh‑токены, аудит.
- `Movie` — основные данные, внешние ссылки (TMDB id).
- `Genre`
- `Hall`
- `Seat` — привязка к залу, статус/координаты.
- `Session` — зал + фильм + время, цены.
- `Order` — пользователь, статус (`Pending`, `Paid`, `Cancelled`).
- `Ticket` — связь с заказом и конкретным местом.
- `Payment` — провайдер, сумма, статусы, external id.
- `UserInteraction`/`UserPreference` — клики и веса для рекомендаций.

## Ключевые потоки
- Бронирование: клиент выбирает места → hold в Redis с TTL 10 мин → создается `Order` со статусом `Pending` → платеж → webhook подтверждает → `Order` → `Paid`, создаются `Ticket`, места переводятся в `Sold`.
- Realtime: SignalR Hub уведомляет подписчиков зала о hold/sold, UI обновляется без перезагрузки.
- Платежи: создание платежа через YooKassa/SBP, webhook валидация сигнатуры, защита от повторной обработки.
- Уведомления: после `Paid` Hangfire job генерирует PDF/QR билета и отправляет email через SMTP; повторные попытки при неудаче.

## План работ (адаптированный под требования)
1. Базовая инфраструктура: настроить проекты, .NET 9, EF Core + PostgreSQL, Serilog, Swagger, JWT pipeline.
2. Домен и CQRS: сущности, миграции, базовые команды/запросы (каталог, сеансы, бронирование).
3. Фронт (JS + SignalR) или Postman‑сценарий: асинхронные вызовы API, realtime карта зала, коллекция тестов.
4. Платежи и интеграции: YooKassa/SBP, webhook, внешние API (TMDB/Dadata), SMTP, Hangfire.
5. Безопасность и hardening: валидация, CSRF/anti‑XSS, авторизация по ролям/permissions, rate limiting.
6. Финализация: админ‑панель для фильмов/сеансов, отчеты, рекомендации, документация по разворачиванию.

## Поэтапный план с критериями готовности
1. Инфраструктура (.NET, БД, Swagger, логирование)
   - Готово, если: решение собирается; работает миграция EF Core в PostgreSQL; Swagger отдает схемы; Serilog пишет в файл.
2. Домен + CQRS слой
   - Готово, если: описаны сущности/enum; применены миграции; реализованы CRUD команды/запросы для Movie/Genre/Hall/Session; валидация через FluentValidation.
3. Бронирование и realtime
   - Готово, если: hold мест в Redis с TTL; команды Reserve/Release/Confirm; SignalR Hub шлет SeatHeld/SeatReleased/SeatSold; фронт или Postman показывает обновление статусов.
4. Платежи и билеты
   - Готово, если: POST /payments/create возвращает redirect/payment_url; webhook меняет Order → Paid и генерирует Ticket; Hangfire job отправляет email через SMTP с билетом (PDF/QR).
5. Безопасность и авторизация
   - Готово, если: JWT login/refresh; роли/permissions проверяются атрибутами/политиками; antiforgery для cookie сценариев (если включены); CSP + rate limiting; проверки владения ресурсами.
6. Внешние интеграции
   - Готово, если: подтягиваем метаданные фильмов из TMDB/Dadata по id/адресу; результаты сохраняются в БД/кешируются.
7. Наблюдаемость и устойчивость
   - Готово, если: глобальный middleware ошибок; структурные логи запросов/ответов; healthchecks для БД/Redis/Hangfire; ретраи отправки писем.
8. UI/Коллекция сценариев
   - Готово, если: страница сеанса делает async fetch и обновляет места через SignalR, или Postman‑коллекция выполняет полный happy path в один клик.
9. Финальное демо
   - Готово, если: собранный чек‑лист требований закрыт; подготовлены ответы “почему так” по архитектуре, безопасности, auth, интеграциям.
